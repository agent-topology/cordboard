# ADR-0001: 격리 수준은 그래프별 설정이며, 기본값은 프로세스 분리다

**Status:** Accepted
**Date:** 2026-09-08
**Deciders:** 단독 (로컬 도구, 저자 = 운영자)
**관련:** ADR-0004 (모델 게이트웨이), ADR-0009 (well-known 두 문서)

> **정정 기록.** 이 결정은 처음에 *"그래프당 프로세스 하나 — 경계를 OS가 강제한다"* 라는 아키텍처 원칙으로 세워졌다. 그 논거는 틀렸다. 결론(기본값은 프로세스 분리)은 유지되지만 **지위가 원칙에서 기본값으로 내려가고, 근거가 바뀐다.** 무엇이 틀렸는지는 Context에 적는다.

---

## Context

### 앞선 논거가 틀린 이유 — 경계는 하나가 아니라 둘이었다

원래 논거는 "한 프로세스 안에서는 `from doc_sync.state import ...` 가 그냥 되고, 이 프로젝트의 목적이 그 경계가 버티는지 확인하는 것이므로 프로세스를 나눠야 한다"였다. 그 문장 안의 "경계"가 두 개를 뭉개고 있었다.

| | 무엇 | 무엇이 지키나 |
|---|---|---|
| **경계 1** | 플랫폼이 그래프 소스를 모른다 | **계약** — HTTP 매니페스트 + Span |
| **경계 2** | 그래프 A가 그래프 B를 import하지 못한다 | 프로세스 |

**이 프로젝트의 테제는 경계 1이다.** 실패 모드 A("플랫폼 저장소에 특정 그래프의 상태 이름이 등장")도, 성공 기준 A·B도 전부 경계 1에 대한 것이고, **프로세스 개수와 무관하게 판정된다.** 한 프로세스에 그래프가 열 개 있어도 카탈로그는 여전히 매니페스트만 읽고 뷰어는 여전히 Span만 읽는다.

프로세스 분리가 실제로 지키는 것은 경계 2뿐이다. 그리고 경계 2는 이 프로젝트의 테제가 아니며, 혼자 쓰는 도구에서 실수로 넘는 일도 아니다 — 의도적으로 해야 되는 일이고, 하는 순간 안다.

### "이유는 RAM이 아니다"도 수사였다

그래프 3개일 때는 맞다. 15개면 도구가 켜지지 않는다. 그리고 **그래프가 늘어나는 것이 이 도구가 성공한 모습이다.** 3~10개라는 초기 가정이 이 결정의 숨은 전제였는데, 그 전제가 깨지는 방향이 곧 성공 방향이다.

### 유스케이스 전수

| 상황 | 프로세스 분리 | 공유 프로세스 |
|---|---|---|
| 파이썬 버전이 다름 | **필수** | 불가 |
| 의존성 충돌 (pydantic v1 vs v2 등) | **필수** | 불가 |
| 무거운 시스템 의존성 (playwright/chromium) | **강함** | 오염 |
| 같은 그래프 v1·v2 공존 | **강함** | 이름 충돌 |
| 디버거 붙이기 | 좋음 — 포트 하나만 | 전체가 멈춤 |
| 하나가 죽어도 나머지 생존 | 좋음 | 같이 죽음 |
| 개발 중 핫리로드 | 대등 | 대등 |
| pytest (플랫폼 없이) | 대등 | 대등 |
| 작은 그래프 15개 | **나쁨** — 유휴 6GB | **좋음** |
| 하루 두 번 3초 도는 그래프 | **나쁨** — 24시간 상주 | 좋음 |
| 무거운 로컬 자원 공유 (임베딩 모델, 벡터 DB) | **나쁨** — N배 | 좋음 |
| 그래프가 그래프를 **동기** 호출 | **문제** (아래) | 서브그래프로 자연스러움 |
| CI에서 전체 기동 | 느림 | 빠름 |

### 원래 검토에서 빠져 있던 선택지 — 지연 기동

처음에는 "전부 상주"와 "하나로 합침" 두 가지만 놓고 골랐다. 세 번째가 있다.

```
cord up          등록만 한다. 프로세스는 안 뜬다
Signal 도착     해당 그래프 프로세스를 그때 기동
유휴 10분       종료
```

inetd / systemd 소켓 활성화와 같은 발상이다. 걸릴 것 같았던 두 가지가 실제로는 안 걸린다.

- **카탈로그가 well-known을 못 긁는다?** 매니페스트는 `cord.yaml`에서 우리가 **생성**한다. 프로세스가 안 떠 있어도 카탈로그는 안다. well-known 엔드포인트는 외부(A2A)용 거울일 뿐이다.
- **HITL 재개가 안 된다?** 재개 요청이 곧 기동 트리거다. 상태는 Postgres에 있다. **애초에 "프로세스가 완전히 종료돼도 재개된다"가 우리 설계의 전제였다.**

비용은 콜드 스타트 2~5초. 웹훅 트리거에는 무의미하고 `cord run` 대화형에만 거슬린다.

## Decision

### 1. 격리 수준은 아키텍처 원칙이 아니라 그래프별 설정이다

```yaml
# cord.yaml
isolation: process        # 기본값
# isolation: {group: light}   # 같은 그룹끼리 한 프로세스
```

플랫폼은 두 모드를 **구분하지 못한다.** 카탈로그·뷰어·라우터 입장에서는 오리진 목록이 다를 뿐이다. 그게 계약 설계의 요점이었다.

### 2. 기본값은 `process`

새 그래프를 만들 때 격리를 고민하지 않아도 되게. 되돌리는 쪽이 명시적 선택이다.

### 3. 판단 규칙을 문서화한다

```
격리한다   파이썬 버전이 다름 · 의존성 충돌 · 무거운 시스템 의존성
           · 버전 공존 · 신뢰하지 않는 코드
공유한다   같은 의존성 · 짧게 실행 · 자주 안 돎 · 개수가 많음
           · 무거운 로컬 자원을 나눠 씀
```

### 4. 지연 기동을 슬라이스 3에 넣는다

트리거 라우터가 생기는 시점이 곧 "Signal 도착 시 기동"이 가능해지는 시점이다. 그때 넣으면 유휴 비용 논쟁의 대부분이 소멸한다.

### 5. 슬라이스 0·1에서는 프로세스 분리를 유지한다

**이건 아키텍처 원칙이어서가 아니라 슬라이스 1의 실험 설계여서다.** 두 번째 그래프를 py3.13 + DeepAgents 템플릿으로 붙여 격리가 실제로 작동하는지 봐야 한다. 실험이 끝나면 기본값을 다시 볼 수 있다.

### 6. 그래프 간 **동기** 합성은 당분간 금지한다

`run.finished` 기반 비동기 체인만 지원한다. 동기 합성이 필요하면 한 그래프 안의 서브그래프로 만든다. 근거와 재검토 조건은 아래.

---

## Options Considered

### Option A: 공유 프로세스 하나

| 차원 | 평가 |
|---|---|
| 복잡도 | 낮음 |
| 자원 | **최선** |
| 격리 | 없음 |
| 다양성 수용 | 파이썬 버전·의존성 충돌 불가 |

**Pros:** 가볍다. 빠르다. 동기 합성이 자연스럽다. CI가 빠르다.
**Cons:** 두 번째 그래프의 의존성이 첫 번째를 깰 수 있다. 슬라이스 1의 실험이 성립하지 않는다.

### Option B: 항상 그래프당 프로세스 (원래 결정)

| 차원 | 평가 |
|---|---|
| 복잡도 | 중간 |
| 자원 | **개수에 비례해 나빠짐** |
| 격리 | 완전 |
| 다양성 수용 | 완전 |

**Pros:** 어떤 조합도 수용. 장애 격리.
**Cons:** 15개 그래프에서 도구가 안 켜진다. 하루 두 번 도는 그래프가 24시간 상주한다. 그리고 **경계 1은 이걸로 얻는 게 아니다.**

### Option C: 그래프별 설정, 기본값 `process` ← **채택**

| 차원 | 평가 |
|---|---|
| 복잡도 | 중간 — 설정 키 하나 |
| 자원 | 조절 가능 |
| 격리 | 필요한 곳에 |
| 다양성 수용 | 완전 |

**Pros:** 두 극단을 다 담는다. 계약이 같아서 플랫폼 코드가 모드를 모른다. 충돌이 터진 그래프만 빼내면 된다.
**Cons:** 판단이 하나 늘어난다 — 판단 규칙 문서화로 완화.

### Option D: 지연 기동

독립 선택지가 아니라 **C에 얹는 것**으로 판단했다. 격리 여부와 직교하며, 채택하면 B의 주된 단점(유휴 비용)이 대부분 사라진다. 다만 트리거 라우터가 전제라 슬라이스 3 이후다.

## Trade-off Analysis

### 결론이 아니라 지위가 바뀐 결정이다

B와 C는 **슬라이스 1까지 동일하게 동작한다.** 차이는 "되돌릴 수 있는가"이고, C가 되돌릴 수 있다. 아키텍처 원칙으로 박아 두면 15번째 그래프에서 원칙을 어기거나 도구를 버리는 두 선택만 남는다.

### 왜 여전히 기본값이 `process`인가

기본값은 **실수의 방향**을 정한다. 기본이 공유면 실수는 "몰랐는데 그래프끼리 얽혀 있었다"이고 발견이 늦다. 기본이 격리면 실수는 "메모리를 좀 더 썼다"이고 즉시 보인다. 후자가 싸다.

### 동기 합성을 금지하는 이유와, 그것이 이 ADR을 뒤집을 조건

동기 합성을 프로세스 분리 상태에서 지원하려면 HTTP 호출 후 대기가 되는데, 그러면 **`1 Run = 1 trace` 결정과 충돌한다.** B의 Run이 A의 Step 아래 자식으로 들어가면 trace 경계가 애매해지고, 타임아웃·실패 전파·취소 전파를 새로 정의해야 한다. 사실상 분산 트랜잭션이다.

`workbench`는 그래프가 하나여서 이 문제를 만난 적이 없고, 우리도 아직 실제 사례가 없다. **사례 없이 설계하면 필요하지 않은 문제를 미리 만드는 것**이므로 금지한다.

**그리고 정직하게 — 동기 합성이 자주 필요해지는 것이 이 ADR을 뒤집을 가장 강한 근거다.** 그때는 해당 그래프들을 한 그룹으로 묶어 서브그래프로 합치는 쪽이 자연스럽다.

## Consequences

### 쉬워지는 것

- 새 그래프를 만들 때 격리를 고민하지 않는다 (기본값이 안전한 쪽)
- 그래프 수가 늘어도 도구를 버리지 않는다 — 그룹으로 묶으면 된다
- 파이썬 버전·의존성이 다른 그래프가 공존한다
- 충돌이 실제로 터진 그래프 하나만 빼내면 되고 플랫폼 코드는 안 건드린다

### 어려워지는 것

- **판단이 하나 늘어난다.** 판단 규칙을 문서로 두지만 여전히 판단이다
- **LangGraph 버전이 좁은 범위에 묶인다.** ← 2026-09-10 추가
  `agent-topology-langgraph`가 검증된 범위(현재 1.2.10–1.2.11)만 지원하고, 벗어나면 그래프를 보기 전에
  `UnsupportedLangGraphVersionError`를 던진다. 매니페스트가 없으면 등록도 안 된다(ADR-0007 R1).
  **"그래프마다 자기 의존성"이라는 이 ADR의 약속에 구멍이 생긴다** — 파이썬 버전은 달라도 되지만
  LangGraph 버전은 공통 범위 안에 있어야 한다. 격리가 이 결합까지 없애 주지는 않는다.
  완화: `cord up`이 각 그래프의 LangGraph 버전을 미리 검사해 기동 전에 알려준다
- **공유 그룹에서는 경계 2가 강제되지 않는다.** 같은 그룹의 그래프끼리 import가 가능해진다. 수용하되, 그룹은 명시적 선택이므로 모르고 당하지는 않는다
- **동기 합성이 안 된다.** 필요한 경우 서브그래프로 우회
- **모드가 둘이라 시험 대상이 둘이다.** 다만 계약이 같아 플랫폼 코드는 하나
- **위험 5(동시성 상태 오염)의 방어가 약해질 수 있다.** 공유 그룹에서는 그래프 간 오염이 다시 가능해진다. 그룹을 쓰기로 한 그래프들에 대해서는 슬라이스 4의 Subject 누출 탐지를 다시 돌려야 한다

### 다시 볼 조건

- **동기 합성이 실제로 필요해지면** → 해당 그래프들을 한 그룹으로 묶고, 그래도 부족하면 이 ADR을 뒤집는다
- **지연 기동이 슬라이스 3에서 잘 동작하면** → 기본값을 더 강하게 유지할 수 있다 (유휴 비용이 사라지므로)
- **슬라이스 1에서 격리가 실제로 아무것도 막지 않는다면** → 기본값을 공유로 바꾸는 것을 검토
- **`agent-topology`의 지원 범위가 넓어지면** → LangGraph 버전 결합이 완화된다. 그쪽 conformance matrix를 주시한다
- **그래프가 10개를 넘으면** → 판단 규칙이 실제로 쓰이는지 점검

## 정정 — 격리를 적는 곳 (2026-09-12)

[ADR-0014](0014-no-graph-descriptors.md)가 cordboard의 그래프 단위 설정을 폐기했다.
이 ADR의 결론 — 기본은 프로세스 분리, 공유 그룹은 명시적 선택 — 은 유지한다. 바뀌는 것은
그 선택을 **어디에 적느냐**다. 어느 그래프들이 한 프로세스를 공유하는지는 Aegra 배포 설정이
이미 표현한다. 같은 배포 파일에 든 그래프는 한 프로세스를 쓰고, 다른 파일은 다른 프로세스를
쓴다. 현재 `aegra/aegra.json`과 `aegra/opaque.json`이 그렇게 나뉘어 있다.

지연 기동 논거의 "매니페스트는 `cord.yaml`에서 우리가 생성한다"도 정정한다. 매니페스트는
그래프 프로세스가 `agent-topology`로 만든다. 프로세스가 떠 있지 않을 때 카탈로그가 아는 것은
마지막으로 등록된 매니페스트다. 프로세스 없이도 카탈로그가 그래프를 안다는 결론은 같고,
근거만 바뀐다.
