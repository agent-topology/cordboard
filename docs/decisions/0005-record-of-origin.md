# ADR-0005: 기록의 원본은 우리 아카이브, Langfuse는 읽는 화면이다

**Status:** Accepted
**Date:** 2026-09-08
**Deciders:** 단독 (로컬 도구, 저자 = 운영자)
**관련:** ADR-0006 (마스킹 강제 지점), ADR-0008 (Outcome 분리)
**슬라이스:** 0에서 아카이브만, 0.5에서 Langfuse 추가

---

## Context

`workbench`는 호스팅 트레이싱 SaaS를 거부한 적이 있다. **이유가 비용이 아니었다** — 무료 구간이 그 프로젝트 규모에 충분했다. 이유는 무료 구간의 보관 기간이 2주인데 그 프로젝트가 답하려는 질문이 몇 주치 이력을 요구한다는 것이었다. 그래서 특정 벤더 소프트웨어에 의존하지 않고 OpenTelemetry의 명명 규약만 빌려 로컬 저장소를 직접 만들었다.

우리 성공 기준 C가 같은 성질이다.

> 지난 **8주간** 모든 그래프에서 Tier가 올라간 Node 상위 10개를 질의 하나로 답한다.

우리는 Langfuse 셀프호스트를 채택했다. 핵심이 MIT이고 계정도 청구 등급도 없다. 여기까지는 필터를 통과한다. 그런데 세 가지가 걸린다.

**하나 — 스키마가 계약이 아니다.** Langfuse는 ClickHouse 스키마가 안정적인 API 계약이 아니라고 명시한다. 메이저 업그레이드와 백그라운드 마이그레이션이 테이블·칼럼·중복제거 동작·조인 패턴을 언제든 바꿀 수 있고, 커스텀 질의는 업그레이드마다 검증하라고 한다. 프로덕션 통합에는 Public API, SDK 질의 헬퍼, MCP 서버, Blob Storage Export를 쓰라고 권한다.

**둘 — 실제로 바꿨다.** v4가 traces와 observations 두 테이블을 하나의 넓은 immutable observations 테이블로 합쳤다. 자체 호스팅 업그레이드 경로는 그 시점에도 작업 중이었다.

**셋 — 보존 정책이 EE다.** 데이터 보존 정책이 엔터프라이즈 라이선스 키를 요구한다. 무한 보존이 기본이라 지금은 유리하지만, 보존을 **우리가 통제하지 못한다**는 사실 자체가 성공 기준 C의 전제와 어긋난다.

정리하면 — **우리는 벤더의 스키마 위에 이력의 원본을 얹으려 하고 있었다.** 그건 우리가 처음부터 거부한 구조다. 호스팅이냐 셀프호스트냐가 아니라, 원본을 남의 형식에 맡기느냐의 문제다.

---

## Decision

### 1. Collector가 두 갈래로 내보낸다

```
그래프 · LiteLLM  →  OTel Collector
                        ├→ 파일 exporter → raw OTLP 아카이브   ← 기록의 원본
                        └→ OTLP exporter → Langfuse            ← 읽는 화면
```

### 2. 아카이브 포맷은 raw OTLP JSON, 날짜별 파일, append-only

```
archive/
├── 2026-09-08.otlp.jsonl.gz
├── 2026-09-09.otlp.jsonl.gz
└── ...
```

가공하지 않는다. Collector가 받은 그대로 쓴다.

### 3. 질의 경로는 둘, 목적이 다르다

| | 경로 | 용도 |
|---|---|---|
| 성공 기준 C | **아카이브 직접** | 정답의 기준. 벤더 무관 |
| UI · 탐색 | Langfuse Public API | 사람이 눈으로 보는 것 |

직접 ClickHouse 질의는 임시 조사용으로만 쓰고, 스크립트에 남기지 않는다.

### 4. 슬라이스 0은 아카이브만, Langfuse는 0.5

원본 경로가 증명되기 전에 컨테이너 여섯 개짜리 스택을 띄울 이유가 없다.

### 5. 질의 엔진은 지금 고르지 않는다

슬라이스 0의 질의는 `jsonl`을 읽는 파이썬 스크립트다. DuckDB든 SQLite든 나중에 얹으면 된다 — **포맷이 raw OTLP인 이상 어떤 엔진도 나중에 붙는다.**

---

## Options Considered

### Option A: Langfuse만. 아카이브 없음

| 차원 | 평가 |
|---|---|
| 복잡도 | **최저** |
| 디스크 | 최저 |
| 8주 이력 보장 | **벤더에 종속** |
| 슬라이스 0 무게 | 무거움 (6 컨테이너) |

**Pros:** 중복이 없다. UI가 공짜로 따라온다.
**Cons:** 스키마 변경이 이력을 끊을 수 있고, 그 위험을 벤더가 직접 경고한다. `workbench`가 거부한 구조의 재현.

### Option B: 아카이브만. Langfuse 없음

| 차원 | 평가 |
|---|---|
| 복잡도 | 낮음 |
| 8주 이력 보장 | **완전** |
| 사람이 보는 화면 | **없음** |

**Pros:** 가장 가볍다. 슬라이스 0에 딱 맞다.
**Cons:** 폭포수 뷰, 검색, 비용 대시보드를 전부 우리가 만들어야 한다. 그건 명시적 out-of-scope다.

### Option C: 둘 다. 아카이브가 원본 ← **채택**

| 차원 | 평가 |
|---|---|
| 복잡도 | 중간 — exporter 하나 추가 |
| 디스크 | 이중 |
| 8주 이력 보장 | **완전** |
| 사람이 보는 화면 | 있음 |

**Pros:** 성공 기준 C가 벤더 변경에 면역. Langfuse를 통째로 갈아치워도 이력이 남는다. 비용은 Collector 설정 몇 줄.
**Cons:** 같은 데이터를 두 번 쓴다. "이거 왜 하지"라는 생각이 반드시 든다(→ Consequences).

### Option D: ClickHouse를 우리 것으로 직접 운영

Langfuse가 쓰는 ClickHouse에 우리 테이블을 따로 만든다.

**Pros:** 질의가 빠르다. 인프라가 하나 준다.
**Cons:** Langfuse의 마이그레이션이 같은 DB를 건드린다. 그리고 로컬 도구에 ClickHouse를 원본 저장소로 두는 건 과하다 — 슬라이스 0에서 파일 하나면 되는 일이다.

---

## Trade-off Analysis

### 중복이 싼 이유

이 결정의 실제 비용은 **Collector 설정의 exporter 하나**다. 코드가 아니다. 그리고 인제스션 경로가 이미 Collector를 지나가므로(ADR-0006) 분기 지점이 공짜로 있다.

반대편 비용은 비대칭적으로 크다. 스키마가 바뀌어 8주 전 데이터를 못 읽게 되는 순간, **그 데이터를 다시 만들 방법이 없다.** 되돌릴 수 없는 손실과 설정 몇 줄의 교환이다.

### 왜 raw OTLP인가

가공하면 그 가공이 곧 스키마 결정이고, 우리가 방금 벤더에게서 피한 문제를 우리 손으로 만드는 셈이다. Raw OTLP는 이미 규격이고, 어떤 OTel 호환 도구도 나중에 읽을 수 있다. `workbench`가 "특정 벤더 소프트웨어에 의존하지 않고 명명 규약만 빌린다"고 한 것의 저장소 판이다.

### 왜 지금 질의 엔진을 안 고르는가

슬라이스 0의 데이터는 수십 줄이다. 그 규모에서 엔진 선택은 정보가 없는 선택이고, 성능이 실제 문제가 되기 전에 고르면 틀린다. 포맷이 표준인 한 엔진은 나중에 붙는다.

---

## Consequences

### 쉬워지는 것

- 성공 기준 C가 Langfuse 없이도 답해진다 — 슬라이스 0이 가벼워지는 직접 원인
- Langfuse 업그레이드가 이력을 위협하지 않는다
- 나중에 Langfuse를 다른 것으로 바꿔도 이력이 남는다
- 보존 정책을 우리가 통제한다 (파일 TTL은 우리 것)

### 어려워지는 것

- **디스크가 두 배.** 로컬 도구 규모에서는 무시 가능
- **"이거 왜 하지"의 유혹.** Langfuse UI에 다 보이는데 아카이브를 왜 유지하나 — 6개월 뒤 반드시 든다. 이 문서가 그때를 위한 것이다
- **중복 제거가 없다.** 재전송으로 같은 span이 두 번 들어올 수 있다. 질의에서 `span_id`로 dedupe해야 한다
- **아카이브에는 UI가 없다.** 사람이 눈으로 볼 때는 Langfuse로 가야 하고, 두 소스가 다를 수 있다 (위험 6과 같은 성질)

### 다시 볼 조건

- **파일 스캔이 느려지면** → DuckDB나 Parquet 변환을 얹는다. 포맷이 raw OTLP인 한 마이그레이션이지 재설계가 아니다
- **Langfuse Public API가 성공 기준 C를 직접 답한다면** → 아카이브를 원본이 아닌 백업으로 강등할지 재검토. 단 스키마 경고가 유지되는 한 강등하지 않는다
- **아카이브가 1년간 한 번도 안 읽혔다면** → 정말 필요했는지 재평가

## 정정 — append와 회전의 실제 계약 (2026-09-11, #5)

Collector contrib `0.148.0`의 file exporter는 `append: true`와 내장 rotation/compression을
동시에 지원하지 않는다. 내장 압축도 gzip이 아니라 zstd다. 따라서 실행 중에는
`archive-YYYY-MM-DD.otlp.jsonl`에 append하고, 수신 날짜를 Collector가 계산해
`cord.archive.date` resource 속성으로 덧붙인다. `TZ=UTC` 실행이 필수다.
span의 과거 실행 시각이나 생산자가 보낸 파티션 값은 파일 날짜를 정하지 않는다.
프로세스 재시작도 같은 날짜 파일을 자르지 않으며 다음 날짜는 별도 파일이다.

Collector를 종료해 파일을 닫은 뒤 지난 날짜 파일만 외부 gzip으로 압축한다.
자동 삭제/크기 회전은 없고 TTL은 무제한이다. 현재 날짜 파일은 압축하지 않는다.
압축된 날짜로 Collector 시계를 되돌려 다시 쓰는 운영은 지원하지 않는다.
운영 명령과 재현 시험은 [아카이브 문서](../archive.md)에 둔다.


## 정정 — 실행 가능한 8주 질의 (2026-09-11, #6)

계획 이름 `query_c.py`는 `cord_runtime.archive_query` 및 `archive-escalations`로
구현했다. Attempt 종료 시각을 정수 나노초로 비교하며 범위는
`(기준 시각 − 56일, 기준 시각]`이다. `escalated`만 Graph ID와 Node 이름으로 묶고,
횟수 내림차순·Graph/Node 오름차순으로 정렬한 뒤 top-N을 적용한다.
부모 검증은 시간 필터보다 먼저 수행한다. 재전송은 span_id로 제거하고 같은 ID의
서로 다른 span 내용은 오류로 처리한다. 수신 날짜 resource 메타데이터는 무시한다.
전체 Run 트리를 입력해야 하며 누락된 부모를 만들어 내지 않는다.
[명령·고정 정답·실제 #5 캡처 검증](../archive-query.md)을 기록했다.


## 정정 — 교환원 경계 (2026-09-11, #7)

[ADR-0013](0013-switchboard-boundary.md)이 모델 소유권의 현재 결정이다.
아카이브와 Collector 계약은 모델 게이트웨이 선택과 무관하다.
LiteLLM은 선택적 생산자 예제이며, 모델 없는 그래프도 같은 아카이브를 사용한다.
