# ADR-0004: 모델 게이트웨이는 LiteLLM 프록시, 승격은 그래프가 소유한다

**Status:** Accepted
**Date:** 2026-09-08
**Deciders:** 단독 (로컬 도구, 저자 = 운영자)
**관련:** ADR-0001 (그래프당 프로세스 분리), ADR-0005 (기록의 원본), ADR-0006 (마스킹 강제 지점), ADR-0008 (Outcome 분리)

---

## Context

`workbench`가 남긴 네 패턴 중 하나는 **모든 노드가 프로바이더 SDK가 아니라 하나의 내부 인터페이스로 모델을 부른다**는 것이었다. 그 이유는 추상화가 아니라 관측이었다 — 실패 후 더 강한 모델로 올라가는 일이 라이브러리 내부 재시도/폴백 안에서 조용히 일어나지 않고, **보이는 추적 가능한 단계**가 되게 하려는 것.

여기에 세 가지 힘이 걸려 있다.

**하나 — 성공 기준 C가 이 결정에 달려 있다.**
"지난 8주간 모든 그래프에서 Tier가 올라간 Node 상위 10개"를 질의 하나로 답해야 한다. 승격이 기록되지 않으면 셀 것이 없다.

**둘 — 그래프 하나가 여러 모델을 부른다.**
한 그래프 안에서 노드마다 다른 모델이 필요하다. 그리고 두 가지 축이 섞여 있다.
- **등급(사다리)** — `fast` → `standard` → `deep`. 순서가 있고, 실패 시 올라간다.
- **능력** — `embed`, `vision`. 순서가 없고, 서로 대체 불가다.

**셋 — 프로세스가 나뉘어 있다.**
ADR-0001에 따라 그래프마다 별개 프로세스다. 각 그래프가 자기 SDK를 직접 부르면 비용 집계 지점과 마스킹 지점이 그래프 수만큼 생긴다.

**제약**
- 오픈소스, 셀프호스트, 계정·청구 등급 의존 금지
- 로컬 노트북에서 뜰 것
- 그래프 저자가 프로바이더 문자열을 알 필요가 없을 것

---

## Decision

### 1. LiteLLM Proxy를 게이트웨이로 채택한다

MIT 라이선스의 셀프호스트 프록시 한 대. 모든 그래프의 모든 모델 호출이 여기를 지난다. 그래프는 OpenAI 호환 스키마 하나로만 말한다.

### 2. Tier와 Model을 가른다

- **Tier** — 우리 어휘. `fast` / `standard` / `deep` / `embed` / `vision`. 프록시의 `model_name` 공개 별칭으로 구현된다.
- **Model** — 프로바이더 문자열. `anthropic/claude-opus-5` 같은 것. **그래프는 이걸 한 번도 보지 않는다.**

모델 교체는 프록시 설정 한 줄이고 그래프 코드 변경은 0줄이다.

### 3. 승격은 그래프가 결정한다

Verdict가 실패를 내면 그래프가 같은 Tier 재시도, 더 높은 Tier 승격, 최종 실패 중 하나를 결정한다. 더 높은 Tier로 보내기로 결정할 때만 직전 Attempt에 `outcome = escalated`를 **선언한다** — 추론하지 않는다.

```
attempt 1   tier=fast       outcome=failed      (다음도 fast: 같은 Tier 재시도)
attempt 2   tier=fast       outcome=escalated   (다음은 deep: 승격)
attempt 3   tier=deep       outcome=passed
```

2번을 같은 Tier로 두는 이유는 "재시도가 도왔나 승격이 도왔나"를 구분하기 위해서다. 그 구분이 이 플랫폼이 존재하는 이유 중 하나다.

> **2026-09-11 정정 (#4).** 첫 예제는 같은 Tier 재시도까지 승격으로 기록했다.
> `fast → fast → deep`의 처분은 `failed → escalated → passed`이며 승격은 정확히 1회다.
> 새 Outcome 값은 추가하지 않는다. [최소 실행 예제](../minimal-graph.md)는 외부 모델 대신
> 고정 응답을 주입해 이 계약을 검증한다. LiteLLM 및 OTLP 통합은 후속 작업이다.

### 4. 금지 A — `router_settings.fallbacks`로 별칭 사이를 건너뛰지 않는다

```yaml
# 금지
router_settings:
  fallbacks: [{"fast": ["deep"]}]
```

### 5. 금지 B — Langfuse 직결 콜백을 쓰지 않는다

```yaml
# 금지
litellm_settings:
  success_callback: ["langfuse"]
```

프록시의 관측 출력은 **OTLP로 Collector에만** 보낸다.

### 6. 허용하는 것

- 같은 `model_name` 아래 여러 배포와 `order` 기반 우선순위 — 프로바이더 장애·429 대응
- `num_retries: 2` 이하 — 한 Attempt 안의 일시적 오류 처리
- 라우팅 전략(simple-shuffle 등) — 같은 별칭 내에서만

### 7. Tier는 선택적이다

노드는 사다리(`tier: {start, escalate_to}`) 또는 고정 별칭(`model: embed`) 중 하나를 선언한다. 사다리 없는 노드에서는 `escalated`가 절대 나타나지 않는다. 정상이다.

### 8. 그래프별 가상 키는 슬라이스 1 이후

`database_url`(Postgres)이 필요하다. 슬라이스 0은 DB 없이 간다.

## Options Considered

### Option A: 게이트웨이 없음 — 각 그래프가 SDK 직접 호출

| 차원 | 평가 |
|---|---|
| 복잡도 | 낮음 |
| 운영 부담 | 없음 |
| 관측 | **불가** |
| 그래프 결합 | 프로바이더 문자열이 코드에 박힘 |

**Pros:** 프로세스가 하나 준다. 슬라이스 0이 가벼워진다.
**Cons:** 승격이 SDK 내부 재시도에 묻힌다. 비용 집계 지점이 그래프 수만큼 생긴다. 마스킹 지점도 마찬가지. `workbench`가 이미 거부한 구조다.

### Option B: LiteLLM 프록시 + 승격은 그래프 소유 ← **채택**

| 차원 | 평가 |
|---|---|
| 복잡도 | 중간 — 프로세스 1개 추가 |
| 운영 부담 | 중간 — 설정 파일 하나, 슬라이스 0에서는 DB 없이 |
| 관측 | **Attempt 단위로 완전** |
| 그래프 결합 | 별칭만. 프로바이더 교체가 무비용 |

**Pros:** 승격이 행이 된다. 비용·마스킹이 한 지점. Tier 교체가 설정 변경.
**Cons:** 프록시가 단일 실패 지점. 설정이 조용히 표류할 수 있다(→ Consequences).

### Option C: LiteLLM 프록시 + LiteLLM `fallbacks`로 승격

| 차원 | 평가 |
|---|---|
| 복잡도 | **가장 낮음** — 그래프에 승격 로직이 없다 |
| 운영 부담 | 중간 |
| 관측 | **파괴됨** |
| 그래프 결합 | 낮음 |

**Pros:** 그래프 코드가 가장 단순하다. 승격 정책이 프록시 설정에 모인다.
**Cons:** 아래 참조. 이게 이 ADR의 핵심 논점이다.

### Option D: 자체 게이트웨이를 만든다

| 차원 | 평가 |
|---|---|
| 복잡도 | 높음 |
| 운영 부담 | 높음 — 프로바이더 스키마 차이를 우리가 흡수 |
| 관측 | 완전 |
| 그래프 결합 | 낮음 |

**Pros:** 완전한 통제.
**Cons:** 프로바이더 어댑터는 이 플랫폼의 요점이 아니라 부수적 배관이다. 100개 넘는 프로바이더를 흡수한 MIT 구현이 이미 있는데 다시 쓸 이유가 없다.

---

## Trade-off Analysis

### 진짜 논점은 B 대 C다

C가 명백히 편하다. 그래프에서 승격 로직이 사라지고, 정책이 설정 파일 한 곳에 모이고, 프록시가 자동으로 처리한다. **그런데 C를 고르면 이 프로젝트의 목적이 사라진다.**

구체적으로 무엇이 죽는가:

| | Option B | Option C |
|---|---|---|
| 그래프가 보는 것 | 실패한 호출, 그 다음 성공한 호출 | 성공한 호출 하나 |
| 기록되는 Attempt | 3개 | **1개** |
| `outcome=escalated` 행 | 있음 | **없음** |
| 성공 기준 C | 술어 하나 + GROUP BY | **답할 수 없음** |
| 재시도 vs 승격 구분 | 가능 | 불가능 |

`workbench`의 4번 항목이 금지한 것이 정확히 C다 — "라이브러리의 내장 재시도/폴백 로직 안에서 보이지 않게 일어나는 것". 우리는 그 결정을 계승한다.

### 가용성과 능력 승격은 다른 축이다

C를 전부 버리는 게 아니다. LiteLLM의 폴백/우선순위 기능은 **다른 목적에는 옳다.**

| | 소유자 | 무엇 |
|---|---|---|
| **가용성** | LiteLLM | 프로바이더가 죽었다, 429다, 리전이 막혔다 → 같은 능력의 다른 배포 |
| **능력 승격** | 그래프 | 출력이 규칙표를 못 넘었다 → 더 강한 Tier |

**구분 기준 한 줄: 기대하는 출력 품질이 바뀌었나.**
바뀌었으면 우리 것, 안 바뀌었으면 LiteLLM 것.

그래서 `fast` 별칭 아래 haiku와 gpt-mini를 두고 `order`로 장애 대응하는 것은 **허용**이다. Tier가 안 바뀌니까. 별칭 사이를 건너뛰는 `fallbacks`만 금지다.

### 금지 B의 근거

프록시가 Langfuse로 직접 쏘면 Collector의 `cord.redacted` 검문소(ADR-0006)를 우회한다. 마스킹 안 된 프롬프트가 저장소에 들어간다. 그리고 그 우회는 **조용하다** — 데이터는 잘 들어오므로 아무도 눈치채지 못한다. 위험 2가 비가역이라는 점을 감안하면 수용할 수 없다.

## Consequences

### 쉬워지는 것

- 모델 교체가 설정 한 줄. 그래프 코드 변경 0줄
- 비용·토큰 집계 지점이 하나
- 마스킹 지점이 하나 줄어든다(그래프 프로세스 + 프록시 두 곳만)
- 다중 모델이 설계 문제가 아니라 설정 문제가 된다
- 승격 질의가 창 함수가 아니라 술어 하나가 된다 (ADR-0008과 맞물림)

### 어려워지는 것

- **프로세스가 하나 늘어난다.** 슬라이스 0의 5개 중 하나가 이것이다
- **프록시가 단일 실패 지점이다.** 죽으면 모든 그래프가 멈춘다. 로컬 도구라 수용
- **승격 로직이 그래프마다 반복된다.** 템플릿과 `cord-runtime` 헬퍼로 완화하되, 중복 자체는 남는다
- **OpenAI 호환 다운컨버전 위험.** 게이트웨이가 요청을 chat-completions 형태로 낮추는 과정에서 일부 프로바이더의 최신 기능이 거부되거나 유실될 수 있다는 보고가 있다. 슬라이스 0에서 실제 프로바이더로 확인해야 한다
- **금지 두 줄이 강제되지 않는다.** 설정 파일은 아무나 고칠 수 있고, 두 금지 모두 "편의 기능을 켜는" 형태라 무심코 켜기 쉽다

### 다시 볼 조건

- 슬라이스 0에서 다운컨버전이 실제 문제로 드러나면 → 해당 노드만 SDK 직접 호출을 예외로 허용할지 재검토
- 그래프가 5개를 넘으면 → 가상 키 + 그래프별 예산을 도입 (DB 필요)
- LiteLLM의 라이선스 경계가 바뀌면 → 필터를 다시 통과시킨다
- 승격 로직 중복이 세 그래프에서 동일해지면 → `cord-runtime`에 정식 API로 승격

## Action Items

1. [ ] `cord up`에 **설정 린트**를 넣는다 — 프록시 설정에 `router_settings.fallbacks` 또는 `success_callback: ["langfuse"]`가 있으면 **기동을 거부**한다. 금지를 문서가 아니라 코드로 만든다
2. [x] #8 슬라이스 0 프록시 설정: `fast` / `deep` 두 별칭, DB 없이, OTLP → Collector만
3. [ ] `cord.yaml` 노드 스키마에 `model:`(고정)과 `tier:`(사다리) 둘 중 하나를 받도록 정의. 둘 다 있으면 검증 오류
4. [ ] `cord-runtime`에 승격 헬퍼 — Attempt span 생성 + `outcome=escalated` 마킹
5. [ ] 슬라이스 0 캘리브레이션에서 다운컨버전 이슈 확인 (실제 프로바이더 응답 검사)
6. [ ] 슬라이스 1: 그래프별 가상 키 도입 시 예산 상한 기능이 무료 범위인지 확인


## 구현 확인 (2026-09-11, #8)

`python -m cord_runtime.proxy_config`가 `fast`/`deep` 설정을 검사하고 DB 없는
LiteLLM 1.87.0을 기동한다. 별칭 간 fallback, 직접 Langfuse 및 다른 callback,
DB·메시지 로깅 설정을 거부한다. 동일 `model_name`의 여러 deployment는 허용한다.
Action 1의 제품 `cord up`은 여전히 계획이며 이 명령이 그 구현을 주장하지 않는다.

최소 그래프의 생성과 검증을 하나의 Attempt 구간으로 묶었다. 기존 헬퍼로 구간을
열고 그래프가 결정한 Outcome을 종료 전에 기록한다. 원자적 다음 Attempt 전환
헬퍼(Action 4)는 별도 미구현이다. 실제 프록시·Collector 테스트가 승격 1회,
모델 매핑 교체 시 승격 0회, 직접 Attempt 부모와 redaction을 확인한다.
실제 프로바이더 검사는 자격증명이 없어 미실행이며 Action 5를 완료하지 않는다.
[설정·검사·smoke 명령과 증거](../model-proxy.md)를 기준으로 삼는다.
