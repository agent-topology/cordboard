# ADR-0006: 비밀값 처리는 redact-secret에 위임하고, Collector가 강제 지점이다

**Status:** Accepted
**Date:** 2026-09-10
**Deciders:** 단독 (로컬 도구, 저자 = 운영자)
**관련:** ADR-0001 (격리 수준), ADR-0004 (모델 게이트웨이), ADR-0005 (기록의 원본)
**전제 충족 (2026-09-11):** `redact-secret==0.1.0b1` 레지스트리 설치와 공개 Python API를 검증했다.

> **갱신 2026-09-10.** 프로젝트가 `redact-secret`에서 **`redact-secret`**으로 이름과 조직이 바뀌었고,
> Rust 코어 마이그레이션이 완료됐다. 실제 구현을 확인해 **세 가지가 이 ADR과 달라졌다** — Decision 항목에 반영한다.
> 당시의 릴리스 대기 상태는 아래 2026-09-11 정정으로 대체한다.

> **정정 기록.** 이 ADR의 첫 판은 "패턴 목록을 직접 관리한다"를 전제로 썼다. 같은 저자가 이미 `redact-secret`을 만들어 두었고, 그것이 이 문서가 손으로 논증하던 구조를 이미 갖추고 있다는 사실을 반영해 전면 재작성한다. 첫 판의 세 겹 구조는 유지되지만 **각 겹이 무엇을 하는지가 달라진다.**

---

## Context

`workbench`는 무엇이든 프로세스를 떠나기 전에 비밀값을 지우는 지점을 **정확히 하나** 두고 싶어 했다. 우리 상황은 그때보다 나쁘다.

**첫째, 배출구가 여럿이다.** ADR-0001에 따라 그래프마다 별개 프로세스이고, 여기에 LiteLLM 프록시(ADR-0004)가 더해진다. 그래프 3개면 4개다.

**둘째, 서버측 마스킹이 유료다.** Langfuse의 인제스션 단계 마스킹은 엔터프라이즈 라이선스 키를 요구한다. 우리 제약을 위반한다.

**셋째, 위험이 비가역이다.** 아카이브가 append-only(ADR-0005)라 한 번 들어간 값은 회수되지 않는다.

**넷째, 실패가 조용하다.** 마스킹이 빠져도 시스템은 정상 동작한다. 데이터가 잘 들어오고 화면이 잘 뜬다. **이게 이 결정의 진짜 설계 문제다.**

### 이미 있는 것

`redact-secret`이 이 문제를 정면으로 다룬다. MIT이고 이 프로젝트와 같은 저자가 관리한다. 핵심 설계가 우리가 필요한 것과 일치한다.

- **탐지와 집행이 분리**된다. 정책이 평문 없는 불변 메타데이터만 받고 `block` / `redact` / `warn` / `allow` 중 하나를 반환한다
- **finding이 평문을 절대 담지 않는다.** 분류·액션·원본 오프셋만 담는다 — 로그가 2차 유출이 되는 경로를 구조적으로 막는다
- **엔트로피는 보조 신호일 뿐**이고, 구조적·문맥적 증거 없이는 분류하지 않는다. 일반 명사 `token` 단독은 의도적으로 무시한다
- **커버리지가 넓다** — PEM 블록, AWS 키, GitHub/GitLab/Stripe/Slack/Vault/Anthropic/OpenAI 토큰, JWT, 자격증명 포함 DB URL, 문맥적 할당(`AWS_SECRET_ACCESS_KEY=`)
- README 상단의 원칙이 우리 결론과 같다 — 클라이언트 측 스캐닝은 예방적 UX이고, 서버 측 스캐닝이 권위 있는 집행 경계다

**그리고 언어 문제가 해소됐다.** Rust 코어와 PyO3 바인딩이 릴리스되어 Python에서 설치된다. 그러면 그래프 프로세스와 LiteLLM 프록시가 **정식 탐지기를 직접 쓴다.**

### 그래서 순서를 정했다

cordboard 슬라이스 0을 먼저 걷게 하고 임시 리댁터를 쓰는 선택지가 있었지만, **redact-secret 릴리스를 먼저** 하기로 했다. 임시 코드가 영구가 되는 걸 피하고, 이 ADR을 한 번만 쓰기 위해서다. 이 순서는 유지하며, 릴리스 가용성은 이제 충족됐다.

## Decision

### 세 겹 + 검증 하나

```
① 그래프 프로세스 (Python)      redact-secret PyO3 바인딩
                                scan_and_redact → 성공 후 cord.redacted=true 스탬프
                                권위 있는 집행. 임시가 아니다

② LiteLLM 프록시 (Python)       같은 패키지, 같은 정책

③ OTel Collector (Go)           cord.redacted가 boolean true가 아닌 Span을 버린다
                                ← 강제 지점. 탐지는 안 한다

④ cord scan-archive              redact-secret CLI 래퍼 (Rust 바이너리)
                                아카이브를 훑어 유출을 보고
                                check 종료 코드: 0 무발견 · 1 발견 · 2 실패
                                실패가 발견보다 우선하고, 비 UTF-8 입력은 fail closed
```

### ③이 하는 일 — 실패를 시끄럽게 만든다

리댁터를 빼거나 잘못 설정하면 **데이터가 새는 게 아니라 안 들어온다.** 그래프 화면이 비고 즉시 눈에 띈다.

| | 조용한 실패 | 시끄러운 실패 |
|---|---|---|
| 리댁터 없음 | 비밀값이 저장됨 | **화면이 빔** |
| 발견 시점 | 사고가 난 뒤 | 즉시 |
| 되돌릴 수 있나 | 아니오 | 예 |

### ③은 탐지하지 않는다 — 이게 의도적이다

Collector도 스캔하게 만들 수 있다. 안 하는 이유는 **그러면 ①이 없어도 시스템이 정상 동작하기 때문**이다. 그 순간 ③은 관문이 아니라 안전망이 되고, 안전망이 있으면 ①은 서서히 사라진다.

Collector가 **버리기만 하기 때문에** ①이 필수로 유지된다. 부수 효과로 Collector는 Go 그대로 두면 되고 FFI가 필요 없다.

### 정책은 기본값을 그대로 쓴다 ← 변경

첫 판은 cordboard가 정책 표를 정의한다고 썼다. **확인해 보니 `redact-secret`의 기본 정책이 그 표와 같다.**

| 탐지 | 기본 액션 |
|---|---|
| 개인키 material | **`block`** |
| 알려진 프로바이더 · bearer/JWT · authorization · 연결 자격증명 | `redact` |
| 그 외 고신뢰 | `redact` |
| 중·저신뢰 | `warn` |

**cordboard는 정책을 정의하지 않는다.** 기본값을 쓰고, 바꿔야 할 이유가 생기면 그때 커스텀 정책 콜백을 넣는다.
정책과 placeholder formatter가 안정적인 확장 지점이다.

`block`은 첫 판에 없던 강도다. 개인키가 span attribute에 들어갔다면 그건 리댁션할 일이 아니라 **그 span 자체가 사고**다.

### 큰 내용물은 애초에 싣지 않는다

프롬프트 전문·diff·모델 출력 전문을 span attribute에 넣지 않는다. `workbench`의 원래 규칙을 계승한다.

**Rust 코어가 되면서 이 규칙의 근거가 바뀐다** — 성능이 아니라 **폭발 반경**이다. 안 실으면 지울 것도, 놓칠 것도 없다.

### 버전은 정확히 고정한다

`redact-secret`은 세 바인딩이 락스텝 버전을 공유한다. cordboard는 **하나의 버전 번호**를 `cord.yaml`이 아니라 `cord-runtime`의 의존성에 고정하고, 업그레이드는 명시적 결정으로 한다.

## Options Considered

### Option A: Langfuse 서버측 마스킹 (EE)

**Pros:** 지점이 하나. 벤더가 관리.
**Cons:** 청구 등급 의존 금지 제약을 정면 위반. 그리고 아카이브 경로는 어차피 못 덮는다.

### Option B: Collector에서만 스캔·마스킹

**Pros:** 그래프 저자가 아무것도 안 해도 된다. 우회 불가.
**Cons:** 비밀값이 그래프 프로세스를 떠나 네트워크를 탄다 — `workbench`의 원래 요구와 어긋난다. Collector가 Go라서 redact-secret을 쓰려면 cgo FFI나 OTLP 프록시 자작이 필요하다.

### Option C: 패턴 목록을 직접 관리 (이 ADR의 첫 판)

**Pros:** 의존성이 없다. 슬라이스 0에서 즉시 시작 가능.
**Cons:** 오탐 폭탄이 되거나 놓친다. 오버랩 해소, placeholder 안전성, 평문 미노출 같은 건 만들다가 당해봐야 아는 것들이고 이미 만들어져 있다. 그리고 **두 구현이 갈라진다.**

### Option D: TS `redact-secret` + Node 사이드카

**Pros:** 기존 구현을 그대로 쓴다.
**Cons:** 평문이 프로세스를 떠난다(B와 같은 문제). 프로세스가 하나 더 늘고, cordboard가 Node 런타임에 묶인다. **Rust 코어 마이그레이션이 이 선택지를 무의미하게 만들었다.**

### Option E: redact-secret PyO3를 ①·②에, Collector는 관문만 ← **채택**

**Pros:** "프로세스를 떠나기 전"(C의 장점)과 "우회 불가"(B의 장점)를 동시에 얻는다. 탐지 로직이 한 곳에 있고 세 언어가 같은 코퍼스로 검증된다. Collector는 Go 그대로.
**Cons:** cordboard가 pre-1.0 패키지에 의존한다. 공개 버전의 호환성을 계속 검증해야 한다.

## Trade-off Analysis

### B·C와 E의 차이는 마스킹이 아니라 강제력이다

실제로 지우는 코드는 어디 두든 같다. 차이는 **안 지웠을 때 무슨 일이 일어나는가**뿐이다.

첫 판에서 이 논점을 한 번 잘못 판단했다 — "라이브러리로 만들면 그래프가 건너뛸 수 있으니 Collector에서 마스킹해야 한다"고 생각했다. 그건 B로 가는 논리였고 "프로세스를 떠나기 전"을 포기하는 것이었다. **관문과 스캐너를 분리하면 둘 다 얻는다.**

### 자체 관리 패키지에 의존하는 것의 양면

`redact-secret`을 같은 사람이 관리한다는 사실은 장점이자 위험이다.

| | |
|---|---|
| 장점 | 필요한 탐지기를 직접 추가할 수 있다. 릴리스를 기다리지 않는다 |
| 위험 | **cordboard의 편의를 위해 redact-secret의 API를 왜곡할 유혹** |

후자를 막는 규칙 하나를 둔다 — **cordboard는 `redact-secret`의 공개 API만 쓴다.** 내부 경로를 참조하지 않고, cordboard 전용 기능을 요청하지 않는다. redact-secret이 cordboard를 모르는 상태로 유지되어야 한다.

### 남는 위험은 수용한다

탐지기가 놓치는 값은 어떤 설계로도 못 막는다. `redact-secret` 자신이 **완전한 DLP 시스템이 아니라고 명시**하고, 잘린·짧은·새로 도입된·미지원 형식은 놓칠 수 있다고 적어 놓았다.

완화는 셋이고, 세 번째가 가장 강하다.

- 새 탐지 요구는 upstream detector로 제안 (로컬 확장 없음)
- `cord scan-archive`가 아카이브를 사후 검증
- **큰 내용물을 애초에 안 싣는다**

## Consequences

### 쉬워지는 것

- 마스킹 실패가 즉시 보인다 — 비가역 위험이 가역 위험으로 바뀐다
- 탐지 로직을 우리가 유지보수하지 않는다
- `block` 액션으로 개인키 유출에 리댁션보다 강한 대응이 가능하다
- finding에 평문이 없어서 관측 로그가 2차 유출 경로가 되지 않는다
- Collector가 Go 그대로 남는다 — FFI도 자작 OTLP 프록시도 없다
- `cord scan-archive`가 정적 바이너리라 Node 런타임 의존이 없다

### 어려워지는 것

- **릴리스 선행 조건은 충족됐다.** 이후 업그레이드도 공개 API와 관문을 다시 검증한다
- **pre-1.0 의존.** API가 바뀌면 cordboard가 따라가야 한다. 버전 고정으로 완화하되 업그레이드마다 비용이 든다
- **두 프로젝트의 릴리스 주기가 얽힌다.** 같은 사람이 하는 이상 우선순위 충돌이 실제로 생긴다
- **개발 중 성가심.** 새 그래프에서 리댁터를 안 붙이면 화면이 빈다 → 관문 차단은 별도 음성 시험으로 확인하고 payload 로그는 켜지 않는다
- **"잠깐만 끄자"의 유혹.** 그리고 그게 영구가 되기 쉽다. 이 문서가 그때를 위한 것이다
- **Collector가 단일 실패 지점.** 죽으면 관측이 멈춘다. 다만 실행은 계속된다 — 관측이 실행을 막지는 않는다

### 슬라이스 0에서 사라진 것

첫 판의 계획에는 "Python 최소 리댁터가 놓친 것을 redact-secret이 아카이브에서 몇 개 잡는가"를 재는 실험이 있었다. **①이 처음부터 정식 탐지기를 쓰므로 잴 격차가 없다.** 종료 판정 ③은 격차 측정이 아니라 단순 확인이 된다.

### 다시 볼 조건

- **redact-secret 새 릴리스가 나오면** → 고정 버전 업그레이드 여부와 관문 회귀를 검증
- **redact-secret의 API가 1.0에서 크게 바뀌면** → 고정 버전 유지 여부를 판단
- **우리 도메인 패턴이 실제로 새면** → upstream detector 제안. 로컬 우회를 만들지 않는다
- **Collector 관문 때문에 개발이 실제로 막히면** → 로컬 개발 모드에서 관문을 경고로 낮추되, **아카이브 exporter는 그 모드에서 비활성화**한다. 원본을 오염시키지 않는다
- **`cord scan-archive`가 반복적으로 유출을 잡으면** → ①의 정책이 너무 느슨한 것. `warn`을 `redact`로 올린다
- **PyO3 휠이 특정 플랫폼에서 안 나오면** → 그 플랫폼에서는 CLI를 사이드카로 부르는 경로를 예외로 검토

## 정정 — 공개 릴리스와 실제 경계 (2026-09-11, #5)

`v0.1.0-beta.1` / Python `0.1.0b1`은 설치 가능하며 릴리스 대기는 해소됐다.
마스킹 없이 아카이브를 시작한다는 RS-5의 이전 문장은 폐기한다.

`ReadableSpan`을 `on_end()`에서 수정하는 대신 공개 `encode_spans()`로 만든
OTLP 복사본을 exporter에서 처리한다. span 값뿐 아니라 resource/scope, 이름,
event, link, status, 중첩 AnyValue와 UTF-8 bytes를 처리한다. 처리 오류나 block은
전체 span을 버리고, 기존 스탬프는 지운 뒤 성공한 경우에만 새로 찍는다.
upstream은 block 범위도 치환하지만 **치환된 텍스트가 있다는 것은 내보낼 권한이 아니다.**
공유 resource/scope에 block이 있으면 그 영향을 받는 모든 span을 버린다.
부모가 차단되어 자식만 남을 수 있으며, 이 경우 계층을 조작해 복구하지 않는다.

Collector는 인증 장치가 아니라 협력하는 로컬 생산자의 처리 누락을 잡는 관문이다.
생산자가 true를 위조하는 공격은 이 스탬프로 막지 못한다. 수신은 loopback에 한정한다.
상세 payload 디버그 로그는 켜지 않는다. 이유를 기록하려고 원문을 유출하지 않는다.
그래프(#4)는 구현됐으나 아카이브 exporter 연결, DeepAgents 및 LiteLLM 실제 연결은 아직 구현되지 않았다.
명령·검증 결과는 [아카이브 실행 문서](../archive.md)에 기록한다.


## 구현 확인 — LiteLLM (2026-09-11, #8)

공개 `CustomLogger`의 async 성공/실패 callback에서 요청의 W3C `traceparent`를
추출하고 해당 Attempt의 자식 model span을 만든다. provider model과 토큰 수만
기록하며 prompt·응답 전문·provider 예외 문자열은 싣지 않는다. 같은 공개 OTel
exporter와 upstream 기본 정책이 프록시 프로세스 안에서 처리한다. 합성 credential
치환과 개인키 span 억제를 실제 Collector 파일에서 검증했다.

기본 OTel callback의 부모 반환 동작은 직접 부모 계약을 만족하지 않아 채택하지
않았다. 내부 메서드 수정이나 저장 후 reparenting 없이 공개 custom callback을 쓴다.
LiteLLM의 payload 가능 콘솔 출력은 배출 전에 버리고, 기동 전 설정 오류만 고정된
설명으로 출력한다. 운영자가 승인한 모델 요청은 provider로 전송된다. 여기의
redaction 경계는 관측 데이터에 적용하며 모델 입력을 변조하지 않는다.
[재현과 한계](../model-proxy.md).


## 정정 — 교환원 경계 (2026-09-11, #7)

[ADR-0013](0013-switchboard-boundary.md)이 모델 소유권의 현재 결정이다.
모든 관측 생산자의 in-process redaction과 Collector gate는 유지한다.
LiteLLM은 선택적인 그래프 의존성이므로 필수 생산자 목록이 아니다.
Cordboard가 외부 프록시의 설정을 검사하는 계획(Action 9)은 철회한다.
이 예제의 callback 검사는 그래프 예제 안에 둔다. 마스킹 계약은 모델 설정을 요구하지 않는다.
