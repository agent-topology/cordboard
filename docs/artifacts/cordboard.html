그래프는 각자 자기 오리진을 갖고 자기 카드를 낸다. cordboard는 그 오리진들을 연결하고, 하나의 어휘로 묶고, 기록의 원본을 직접 들고 있는다. 교환원이 하던 일 — 연결하고 기록한다.

직접 만든다 · 직접 소유한다 가져온다 그래프가 소유 · 각자 격리

전제. 여러 팀이 쓰는 사내 플랫폼이 아니라 혼자 쓰는 로컬 도구이고, 다음 프로젝트를 위한 학습 매체다.

그래서 규약 강제 수준은 낮춰도 되고, 대신 만들고 띄우는 마찰이 훨씬 중요해진다. "노트북에서 계정 없이 뜬다"가 부가 조건이 아니라 주 조건이다.

슬라이스 0 — 걷는 뼈대

질문 하나에만 답한다 — "Tier가 올라간 Node"를 우리 데이터로 실제로 셀 수 있는가. 성공 기준 C가 이 프로젝트에서 가장 비싼 미지이고, 틀렸다는 걸 6주 뒤에 알면 그 6주치 데이터가 통째로 못 쓰게 된다.

그래프 하나 — 플랫폼 없이

노드 셋의 고정 위상 fetch → draft → verify. draft가 fast Tier에서 규칙표를 통과 못 하도록 일부러 설계한다. 승격이 관측 대상이므로 재현 가능하게 실패해야 한다. cord new는 아직 없다 — 손으로 쓴다. 가짜 토큰을 프롬프트에 미리 심어 둔다.

완료 — 플랫폼이 하나도 안 떠 있는 상태에서 pytest가 통과한다.

cord-runtime v0 + Collector

둘을 같이 만든다. 따로 만들면 둘 다 검증이 안 된다. SpanProcessor가 패턴을 지우고 cord.redacted=true를 찍는다. 헬퍼가 Run / Step / Attempt span을 만든다. Collector는 OTLP를 받아 cord.redacted가 없으면 버리고, 파일 exporter로 내보낸다.

완료 — 한 번 돌리면 아카이브에 span이 쌓이고, SpanProcessor를 주석 처리하면 파일이 빈다.

질의 스크립트 초안 — 관문

아카이브를 읽어 "Tier가 올라간 Node"를 센다. 데이터가 몇 줄뿐이라 답이 맞는지 눈으로 확인할 수 있다. 여기서 반드시 확정할 것 — Attempt가 부모 Step 아래 형제 행으로 서 있는가. 아니면 GROUP BY가 아니라 JSON 파싱이 되고, 그건 성공 기준 C의 실패다.

완료 — 질의가 답을 낸다. 그리고 Attempt 계층을 한 번 일부러 잘못 만들어 보고 질의가 깨지는 걸 확인한다.

LiteLLM 프록시

fast / deep 두 별칭만. DB 없이 시작한다 — 가상 키와 예산은 이 슬라이스의 질문과 무관하다. 그래프의 모델 호출을 프록시 경유로 바꾸고, 프록시의 otel 콜백도 같은 Collector로 보낸다.

완료 — 승격이 하드코딩이 아니라 실제로 일어나고, 프록시가 낸 span도 아카이브에 있다.

Aegra

설정 파일은 손으로 쓴다 — 생성은 슬라이스 1. Postgres 하나. POST /threads → POST /threads/{id}/runs로 실행하고 호출에 traceparent를 주입한다.

완료 — 프로세스 경계를 넘어도 span이 한 trace로 묶인다. 고아 span 0건.

종료 판정 셋

① 질의가 "Tier가 올라간 Node 상위 N개"를 답한다.
② 리댁터를 끄면 아카이브에 아무것도 안 들어온다.
③ 심어 둔 가짜 토큰이 아카이브 어디에도 없다 — grep으로 확인.

셋 다 통과해야 슬라이스 0.5로 간다. 하나라도 실패하면 아카이브 포맷이나 Attempt 계층을 다시 잡는다 — 지금은 데이터가 다섯 줄이라 공짜다.

층별로 자르지 않는다. "Collector를 다 만들고 → 뷰어를 다 만들고"로 가면 마지막까지 아무것도 검증되지 않는다. 각 슬라이스는 얇지만 한쪽 끝에서 다른 쪽 끝까지 관통하고, 가장 비싼 미지를 가장 먼저 만난다.

경계

호스트가 그래프 소스를 import하지 않는다는 것과, 플랫폼이 그래프의 생애주기를 모른다는 것은 다른 얘기다. npm은 당신 패키지를 자기 프로세스에 링크하지 않지만 만들고 배포하고 설치하고 실행하는 법은 전부 안다.

하는 것

  • 1그래프 카탈로그 — 오리진들의 두 문서를 긁어 하나로 답한다. 등록 시 검증도
  • 2공용 어휘층 — 하나의 Span 모양. Collector에서 돌고, 마스킹의 강제 지점이다
  • 3데이터에서 파생되는 뷰어 — 뷰어 코드에 어떤 그래프의 Node 이름도 없다
  • 4선언적 트리거 라우터 — 새 Rule마다 코드를 쓰지 않는다
  • 5그래프 패키지 생애주기 — scaffold · 선언 · 편입 · 기동
  • 6기록의 원본 — raw OTLP 아카이브. 벤더 스키마에 이력을 맡기지 않는다

명시적으로 하지 않는 것

  • ×실행 런타임 — Thread·체크포인트·재개·취소·스트리밍은 Aegra
  • ×오케스트레이션 프레임워크 — LangGraph도 DeepAgents도 대체하지 않는다
  • ×트레이스 저장 엔진 — Langfuse + ClickHouse. 단 그것이 원본은 아니다
  • ×의존성 해석 — uv 워크스페이스
  • ×마켓플레이스 · 레지스트리 — 우리 그래프는 이식 가능한 상품이 아니다
  • ×노코드 빌더 · 평가 플랫폼 · 프롬프트 관리
  • ×멀티테넌시 · 과금 · SSO
  • ×프로덕션 배포 — k8s, CI/CD, 시크릿 관리, 롤아웃
실패 모드 A

두 번째 모노리스

플랫폼이 그래프 내부를 너무 많이 알게 된다. 새 그래프를 붙이려면 플랫폼 코드를 고쳐야 한다.

증상 — 플랫폼 저장소에 특정 그래프의 상태 이름이 등장하는 순간.

실패 모드 B

아무것도 아닌 층

너무 얇아서 Aegra와 Langfuse를 그냥 쓰는 것보다 나은 게 없다.

증상 — 이 플랫폼을 걷어내도 아무도 불편해하지 않는 순간.

그래프 하나 = 레포 하나

레포 전체가 하나의 관리 단위다. 계약은 루트의 cord.yaml 하나이고, 나머지 산출물은 전부 여기서 생성된다.

고정 위상. workbench가 이 모양이다 — 읽기 → 검증 → 초안 → 승인 → 게시. 에이전트 루프가 아니다.

DeepAgents 기반

create_deep_agent()가 CompiledStateGraph를 반환하므로 우리 entrypoint에 그대로 맞는다. 도구 루프가 실제로 필요할 때만.

  • +미들웨어가 계측·마스킹의 in-process 삽입점이 된다
  • +interrupt_on 이 도구 단위 승인을 선언으로 준다
  • −파일시스템·요약·서브에이전트가 기본 스택으로 딸려 온다
  • −문서의 기본 경로가 LangSmith를 가리킨다 — 미들웨어로 우회

DeepAgents는 플랫폼 구성요소가 아니라 Graph 박스 안에 있다. 우리 6개 능력과 겹치는 것은 0개다. 기반으로 강제하면 그래프 층에서 실패 모드 A를 다시 만드는 셈이라 템플릿 선택지로만 둔다. 다만 cord-runtime은 OTel SpanProcessor와 DeepAgents 미들웨어 두 형태로 같은 로직을 낸다.

각 프로세스가 내는 두 문서

/.well-known/agent-card.json

A2A 스펙 그대로. 우리 필드는 하나도 넣지 않는다. 바깥에서 이걸 어떻게 부르는지에 대한 답이다.

Linux Foundation 프로젝트이고 스펙은 1.0. 공개된 카드 다수가 스펙을 안 지키는 상황이라 정확히 내는 것 자체가 기여가 된다.

채택 · 확장 없음
/.well-known/agent-topology.manifest.json

Node, Edge, Tier, Trigger. 안이 어떻게 생겼는지에 대한 답이다. 뷰어가 먹는 것이 이쪽.

Agent Card는 의도적으로 내부를 감추는 불투명 계약이라 이 역할을 못 한다. 두 문서는 경쟁하지 않는다.

직접 정의 · 이름은 아직 선점하지 않음

agent-graph.json이 아닌 이유 — RFC 8615는 새 well-known URI 등록을 요구하고, 특정 애플리케이션용 이름은 구체적이어야 하며 일반 용어 선점은 권장하지 않는다고 명시한다. RFC의 예시가 metadata가 아니라 example-metadata다. 이름은 얻는 것이지 잡는 게 아니다.

격리 수준 — 원칙이 아니라 기본값

정정. 이건 처음에 "경계를 OS가 강제한다"는 아키텍처 원칙으로 세웠다가 논거가 틀려서 강등된 결정이다. 경계가 하나가 아니라 둘이었다.

경계 1 — 이 프로젝트의 테제

플랫폼이 그래프 소스를 모른다.

계약이 지킨다 — HTTP 매니페스트 + Span. 프로세스 개수와 무관하다. 한 프로세스에 그래프가 열 개 있어도 카탈로그는 매니페스트만, 뷰어는 Span만 읽는다. 실패 모드 A도 성공 기준 A·B도 전부 여기에 대한 것이다.

경계 2 — 곁가지

그래프 A가 그래프 B를 import하지 못한다.

프로세스가 지킨다. 다만 테제가 아니고, 혼자 쓰는 도구에서 실수로 넘는 일도 아니다 — 의도적으로 해야 되는 일이고 하는 순간 안다.

"이유는 RAM이 아니다"도 수사였다. 3개일 때는 맞지만 15개면 도구가 안 켜진다. 그리고 그래프가 늘어나는 것이 이 도구가 성공한 모습이다.

기본값

isolation: process

기본값은 실수의 방향을 정한다. 기본이 공유면 실수는 "몰랐는데 얽혀 있었다"이고 발견이 늦다. 기본이 격리면 실수는 "메모리를 좀 더 썼다"이고 즉시 보인다. 후자가 싸다.

  • 격리파이썬 버전이 다름 · 의존성 충돌
  • 격리무거운 시스템 의존성 · 버전 공존
  • 공유같은 의존성 · 짧게 실행 · 자주 안 돎
  • 공유개수가 많음 · 무거운 로컬 자원을 나눠 씀
슬라이스 3

지연 기동 — 원래 안 봤던 선택지

cord up은 등록만 하고, Signal이 오면 그때 기동하고, 유휴 10분에 종료한다. inetd와 같은 발상. 채택하면 상주 비용 논쟁의 대부분이 소멸한다.

  • +20개 등록, 상주 1~2개
  • +매니페스트는 cord.yaml에서 생성하므로 카탈로그는 프로세스 없이도 안다
  • +재개 요청이 곧 기동 트리거 — 상태는 Postgres에 있다
  • −콜드 스타트 2~5초. cord run 대화형에서만 거슬린다

플랫폼은 두 모드를 구분하지 못한다 — 오리진 목록이 다를 뿐이다. 그게 계약 설계의 요점이었다. 슬라이스 0·1에서 프로세스 분리를 유지하는 것도 원칙이어서가 아니라 슬라이스 1의 실험 설계여서다. 그리고 남은 열린 문제 하나 — 그래프 간 동기 합성은 1 Run = 1 trace와 충돌해서 당분간 금지한다. 그게 실제로 자주 필요해지면 이 결정을 뒤집을 가장 강한 근거가 된다.

Signal의 출처는 GitHub이 아니다

Rule 라우터는 출처를 모른다. GitHub 웹훅은 http 종류의 한 사례일 뿐이다.

schedule매일 09:00 — Aegra가 cron을 이미 준다
file~/notes/**.md 변경 — 로컬 도구라 오히려 자주 쓸 것. 슬라이스 3의 주 시험 대상
manualcord run doc-sync — 개발 중 대부분의 실행
http아무 웹훅. 로컬에서 터널링 마찰이 커서 슬라이스 3에서 뒤로 밀린다
run.finished다른 Run의 종료. 그래프끼리 엮이는 지점 — 아무도 안 해 주는 일이라 실패 모드 B에 대한 방어이기도 하다. when 절이 필수이고 체인 깊이 상한이 붙는다

Subject도 이슈가 아니라 그냥 URI다 — github:issue/482, file:~/notes/api.md, run:0193f…, manual:2026-09-08T14:22.

불행 경로와 결정

01

같은 Signal이 두 번

웹훅 중복 발송은 정상 동작이다.

signal_id로 중복 제거 + (assistant, subject) 동시성 정책. 기본 skip.

02

부작용이 두 번 실행

재개하면 인터럽트된 노드가 처음부터 다시 돈다.

템플릿이 구조로 회피 · 부작용 노드는 멱등성 키 · 뷰어가 중복 Step을 감지.

03

재개 값이 하나인데 인터럽트가 여럿

RuntimeError. 대기 중 인터럽트가 여럿이면 ID 지정이 필수다.

Approval은 항상 interrupt_id를 동반한다. 하나뿐일 때도 예외 없이.

04

아무도 승인하지 않는다

Run이 영원히 멈춰 있다. 주인이 없던 자리.

만료 정책은 Manifest가 선언하고 집행은 플랫폼이 한다. 그래프는 만료를 몰라도 된다.

05

프로세스가 죽는다

Mode 2에서는 이어받을 워커가 없다.

수용. cord up 재기동 시 Aegra 리스 복구가 작동. 카탈로그는 unreachable 표시, Signal은 보류.

06

Run이 Run을 무한히 부른다

run.finished가 Signal이 되면 순환이 가능해진다.

chain.depth 상한 5 · 자기 루프 차단 · run.finished Rule은 when 절 필수.

07

트레이스가 경계에서 끊긴다

라우터·그래프·프록시가 전부 별개 프로세스다.

W3C Trace Context 표준대로. 단 체인된 Run은 새 trace — 넣으면 1 Run = 1 trace가 깨진다. caused_by로 잇는다.

08

Signal이 아무 Rule에도 안 맞는다

조용히 사라지고 있었다.

매칭 실패도 기록한다. signal_id, 페이로드 요약, 시도한 Rule 목록.

위험 순위와 처분

되돌리기 비용 × 확률로 줄을 세우면 대응이 갈린다. 위 둘은 설계가 걸려 있어 지금 풀었고, 나머지는 완화하거나 애초에 닿지 않게 했다.

위험비용 / 확률처분
1 어휘층을 Langfuse에 얹는 방식성공 기준 C가 여기 걸려 있다 최상
높음 슬라이스 0에서 검증한다 — 세 갈래. ① Attempt를 metadata가 아니라 자식 observation 행으로. 승격이 JSON 파싱이 아니라 GROUP BY가 된다. ② 질의는 Public API가 1차 경로. 직접 ClickHouse는 임시 조사용. ③ Langfuse는 읽는 화면이지 기록의 원본이 아니다. Collector가 raw OTLP를 우리 아카이브로 한 벌 더 쓴다. Langfuse가 ClickHouse 스키마는 안정적 API 계약이 아니며 업그레이드마다 커스텀 질의를 검증하라고 직접 경고한다.
2 마스킹이 프로세스 밖에서한 번 새면 회수 불가 최상 · 비가역
중간 3중, Collector가 강제 지점. 그래프 안의 SpanProcessor가 지우고 cord.redacted를 찍는다. LiteLLM 프록시도 같은 처리. 그리고 Collector가 cord.redacted 없는 Span을 거부한다. 리댁터를 빼면 조용히 새는 게 아니라 화면이 비어서 즉시 눈에 띈다. 남는 위험은 패턴 목록이 놓치는 값 — 수용하고 cord.yaml에서 그래프별 추가를 허용한다.
3 인터럽트 앞 이중 실행LangGraph 미해결 이슈 #6208 높음
높음 우리가 고칠 수 없다. 닿지 않게 한다 — 템플릿이 인터럽트 노드를 부작용 없는 빈 노드로 만들고, 부작용 노드는 (subject, node, attempt) 멱등성 키를 갖고, 뷰어가 인터럽트 전후 같은 Node의 중복 Step을 경고한다. 슬라이스 2에서 의도적 실패로 시험.
4 병렬 인터럽트 ID 충돌미해결 이슈 #6626 중간
낮음 등록을 거부한다. 걸리면 그 Run은 영원히 재개 불가라 경고로는 약하다. Manifest의 edges에서 병렬 분기가 보이고 그 안의 노드가 interrupts: true면 카탈로그가 막는다. 막을 수 있는 것만 막는다 — 3번은 코드를 못 보니 못 막고, 4번은 Manifest만으로 보이니 막는다.
5 동시성 상태 오염격리가 기본값인 동안만 그래프 간이 사라짐 높음
낮아짐 같은 그래프의 서로 다른 Run 사이에는 남아 있다. max_in_flight: 2로 상한을 낮춘다. 그리고 DeepAgents 문서가 같은 위험을 직접 경고한다 — 서브에이전트·병렬 도구·다른 스레드의 병렬 호출이 동시에 도니 훅에서 인스턴스 속성을 바꾸지 말고 그래프 상태에 두라는 것. 상태는 스레드 범위라 동시성 하에서 안전하다. 템플릿 규칙으로 박고, 슬라이스 4에서 Subject 누출 탐지로 시험한다. 공유 그룹을 쓰는 그래프가 생기면 그래프 간 오염이 다시 가능해지므로 그 그룹에도 같은 탐지를 돌린다.
6 뷰어 이중 데이터 소스Langfuse 인제스션은 비동기다 낮음
높음 화면이 잠깐 어긋날 뿐 데이터는 안 상한다. 숨기지 말고 드러낸다 — Run 카드에 진행 중(라이브) / 기록됨 배지. 끝난 Run은 Langfuse에 도달할 때까지 SSE 결과를 붙들었다 교체.

Thread는 묶는 도구가 아니다
